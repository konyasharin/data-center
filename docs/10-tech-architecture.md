# Техническая архитектура

**Обязательно к прочтению до написания кода.**

## Главный принцип: данные отдельно, визуал по требованию

Аналогия: виртуализированный список. Данные в сторе, DOM-узлы только для
видимых строк. Никто не хранит значение ячейки внутри `<div>`.

```csharp
// ❌ ловушка: состояние живёт внутри ноды
public partial class Server : Node3D {
    public float Temperature;
    public float SmartHealth;
}
```

Дальше логика железная: удалить ноду = потерять состояние → удалять нельзя →
ноды живут вечно → потолок в несколько тысяч объектов, и фаза 5 не наступает.

```csharp
// ✅ данные — всегда, в массивах на уровне зала
public sealed class HallData {
    public float[] Temperature;    // индекс = слот
    public float[] SmartHealth;
    public float[] UptimeHours;
    public byte[]  Status;
}
```

Визуал — чистая производная, которую можно выбросить и пересоздать без
последствий. Симуляция не знает, смотрит ли на неё кто-то.

## LOD у всего

### Сервер

| LOD | Когда | Представление |
|---|---|---|
| L0 | стойка открыта, игрок в 3 м | отдельная запись: температура, SMART, аптайм, конкретные диски |
| L1 | игрок в зале | строка в массиве зала, обновление пачкой 1 раз/сек |
| L2 | зал не виден | **не существует индивидуально**: агрегат зала (N серверов, средняя λ, утилизация) |
| L3 | другая площадка | одно число на площадку, тик раз в игровой час |

### Отказы: выбирать, а не симулировать

```
ожидаемых_отказов = N * λ * dt
k = poisson_sample(ожидаемых_отказов)      # обычно 0..3
→ выбрать k случайных индексов, материализовать как задачи
```

Стоимость O(число отказов), не O(число серверов). Миллион серверов на десяти
площадках — десяток операций за тик.

При входе игрока в зал конкретные состояния **достраиваются детерминированно** из
seed зала + прошедшего времени, чтобы мир не «телепортировался» при приближении.

### Работник

| LOD | Условие | Стоимость |
|---|---|---|
| L0 | в поле зрения, <30 м | полный скелет, анимации, IK, взаимодействие с объектами |
| L1 | виден, 30–100 м | `MultiMesh` + запечённая анимация в текстуру (VAT), без скелета |
| L2 | в загруженном зале, не виден | только позиция вдоль маршрута, тик 2 Гц, без рендера |
| L3 | вне загруженной зоны | **бригада как единица**: «4 человека, задача X, готово в 14:30» |

Целевой бюджет (уточнить профилированием): ~40–80 персонажей на L0, ~300 на L1,
остальные L2/L3. Тела берутся из пула и привязываются к id, а не создаются под
каждого работника.

## Тики

| Частота | Что считает |
|---|---|
| кадр (60 Гц) | рендер, камера, интерполяция позиций, взаимодействие игрока |
| 4 Гц | движение агентов, выбор задачи, поиск пути |
| 1 Гц | тепло, питание, сеть, утилизация по залам |
| 1 игровой час | экономика, рынок, поставки, обучение моделей, найм |

Всё, кроме кадра, — в `WorkerThreadPool`, результат применяется в главном
потоке. Рендер интерполирует между тиками, поэтому 4 Гц выглядит плавно.

**Все тики принимают `dt` в игровых секундах и обязаны быть корректны при
`dt = 3000 с`** (см. `09-interface-time.md`).

## Рендер стоек

Зал на 200 стоек x 42 юнита = 8400 серверов в кадре. Нодами — смерть.

- **Стойка** = одна модель (корпус + рельсы), `MultiMeshInstance3D` на весь ряд.
- **Серверы** = `MultiMesh` внутри стойки, один инстанс на юнит, трансформы
  пишутся один раз.
- **Индикаторы** — не источники света и не отдельные меши. Состояние всех юнитов
  зала кодируется в **текстуру состояний** (пиксель = юнит), шейдер читает её и
  рисует мигающие LED. Обновление — запись в `Image` раз в секунду. Один draw
  call на тысячи лампочек.
- **Свет в залах** — запечённый `LightmapGI`. Динамических источников минимум:
  фонарь игрока, аварийное освещение.
- **Кабели** — не физика и не по одному мешу. Процедурная геометрия жгутов,
  пересобирается только при изменении коммутации. LOD: вблизи отдельные провода,
  издали — жгут одной трубой.
- **Прицеливание** в конкретный юнит считается математикой по позиции луча, а не
  коллайдерами на каждом сервере.

## Навигация без навмеша

ЦОД — это коридоры между рядами, то есть граф, а не открытое поле.

- **Граф путевых точек** строится автоматически при расстановке стоек: проходы
  между рядами, двери, лестницы.
- Поиск пути — A* по графу из сотен узлов вместо `NavigationServer3D` по
  полигонам. Дешевле и, что важнее, **детерминированно** — можно посчитать время
  выполнения задачи, не двигая агента вообще (это и есть L3).
- Локальное расхождение — spatial hash + отталкивание, только на L0/L1.
- **Работникам не выдаются физические тела.** `CharacterBody3D` на тысячу
  агентов не вывезет.

## Стриминг мира

- Каждое помещение (зал, склад, офис, машзал, подстанция) — отдельная сцена,
  грузится через `ResourceLoader.LoadThreadedRequest` по близости и прямой
  видимости.
- Окклюзия: ЦОД — идеальный случай, глухие стены отсекают почти всё. Конкретный
  способ зависит от выбранного рендерера, см. `13-open-questions.md`.
- Между зданиями — улица кампуса, единственное открытое пространство, там LOD
  зданий агрессивный.
- Переход между площадками в фазе 5 — экран загрузки, и это нормально.

## Что на чём писать

- **Ядро симуляции** (массивы серверов, работники, задачи, тепло, экономика) —
  **C#**. GDScript для циклов по десяткам тысяч элементов не годится.
- **Данные — структуры массивов**, не объекты на сущность.
- **GDScript** — UI, скриптуемые события, настройки, прототипирование правил.
- Прямые вызовы `RenderingServer` в обход нод там, где инстансов тысячи.
- `sim/` не ссылается на `Godot.Node`: ядро должно собираться и тестироваться
  без сцены.

## Профилирование

Профилировать **с самого начала на синтетическом позднем гейме**: скрипт,
генерирующий 5 площадок x 20 залов x 2000 работников, и замер. Делать это в
конце — классический способ переписать проект.
